# 멀티 도메인 관리

## 멀티 도메인이란?

하나의 Mublo 설치로 여러 개의 독립적인 사이트를 운영할 수 있습니다. 각 도메인은 회원, 설정, 테마, 권한, 콘텐츠가 완전히 분리됩니다.

```
하나의 서버
├── example.com       → 사이트 A (회원/설정/테마 독립)
├── shop.example.com  → 사이트 B (회원/설정/테마 독립)
└── blog.example.com  → 사이트 C (회원/설정/테마 독립)
```

## 도메인 추가

관리자 > 도메인 관리 > 도메인 추가

### 기본 정보

| 항목 | 설명 |
|------|------|
| 도메인명 | `shop.example.com` (DNS에 등록된 도메인) |
| 사이트 제목 | 브라우저 탭에 표시 |
| 상태 | 활성/비활성/차단 |
| 계약 유형 | 무료/월간/연간/영구 |
| 계약 기간 | 시작일 ~ 종료일 |

### 제한 설정

| 항목 | 설명 | 기본값 |
|------|------|--------|
| 저장소 제한 | 업로드 파일 용량 한도 | 1GB |
| 회원 수 제한 | 등록 가능 회원 수 | 무제한 |

### DNS 설정

도메인을 추가하기 전에 DNS에서 해당 도메인이 서버 IP를 가리키도록 설정해야 합니다.

```
shop.example.com  → A 레코드 → 서버 IP
```

## 도메인(호스트명) 변경

등록된 사이트의 주소를 바꿉니다. **최고관리자(is_super)만** 실행할 수 있고, 대상은
자기 도메인(현재 접속 중인 도메인)과 하위 도메인입니다.

`도메인 관리` 목록에는 자기 도메인과 하위 도메인이 함께 나오며, 지금 접속 중인 도메인에는
`현재 접속` 배지가 붙습니다. 변경은 해당 행의 수정 화면에서 합니다.

자기 도메인 행은 **모든 관리자에게 보이지만**(자기 사이트 주소는 확인할 수 있어야 하므로),
호스트명 변경 화면은 최고관리자에게만 열립니다. 또한 그 행은 일괄 수정·삭제 대상에서 제외됩니다
(자기 자신을 비활성·삭제해 접속이 끊기는 것을 막기 위함).

### 절차

1. 바꿀 도메인의 DNS를 이 서버로 먼저 설정한다 (A/AAAA 또는 CNAME).
2. 수정 화면의 **도메인(호스트명) 변경**에 새 도메인명을 입력하고 `DNS 확인`을 누른다.
3. 확인을 통과하면 재입력란이 열린다. 새 도메인명을 다시 입력하고 `도메인 변경`을 누른다.

### DNS 확인은 무엇을 보는가

| 신호 | 용도 |
|------|------|
| DNS 조회 (A/AAAA/CNAME) | 보고용. 무엇이 빠졌는지 화면에 표시 |
| 도달 확인(프로브) | **합격 판정**. 새 호스트명으로 실제 HTTP 요청을 보내 이 설치본이 응답하는지 확인 |

판정을 프로브로 하는 이유는, A 레코드와 서버 IP를 비교하는 방식이 Cloudflare 같은
프록시/CDN 뒤에서는 항상 실패하기 때문입니다. 프로브는 경로가 몇 단이든 "결국 이 사이트에
도달했다"를 직접 확인합니다.

| 판정 | 의미 | 결과 |
|------|------|------|
| `reachable` | 새 호스트명으로 이 서버에 연결됨 | 변경 가능 |
| `dev_local` | 개발환경(`APP_ENV`가 local/development/dev/testing) + 로컬 호스트라 도달 확인 생략 | 변경 가능 |
| `dns_missing` | A/AAAA/CNAME 레코드가 없음 | 반려 |
| `unreachable` | DNS는 있지만 이 서버로 연결되지 않음 | 반려 |

`unreachable`은 응답 코드에 따라 원인 힌트가 함께 표시됩니다.

| 응답 코드 | 안내 |
|---|---|
| 200 (nonce 불일치) | 응답은 왔지만 이 설치본이 아님 — 그 호스트명이 다른 사이트로 연결됨 |
| 404 | 다른 서버가 응답했거나, 연결된 오리진에 이 버전이 배포되지 않음 |
| 401 / 403 / 429 / 503 | 프록시·보안 설정(Cloudflare 봇 차단·챌린지, IP 제한)에 막힘 → `/.well-known/mublo-domain-verify`를 예외 처리 |
| 502 / 521 / 522 / 523 / 525 | 프록시가 오리진 서버에 연결하지 못함 |
| 3xx | 리다이렉트 반복 — 프록시의 HTTPS 강제 설정 확인 |

### CDN·프록시(Cloudflare 등) 경유

프록시를 거쳐 인증서를 대신 처리하는 구성도 그대로 동작합니다. 프로브는 IP를 비교하지 않고
"결국 이 설치본이 응답했는가"만 보기 때문입니다(A 레코드가 프록시 IP여도 무관).

- **Flexible SSL**(오리진은 평문 http, 인증서는 프록시가 처리) — 동작합니다.
- **Full / Full(strict)** — 동작합니다. 프로브는 도달 확인이 목적이라 TLS 인증서를 검증하지 않습니다.
- **HTTPS 강제(301)** — 리다이렉트를 3회까지 따라갑니다(http/https 프로토콜만).
- **캐시** — 쿼리스트링이 붙은 비정적 경로이고 nonce가 매번 달라 캐시되지 않습니다.

주의할 점 두 가지:

1. **WAF·Bot Fight·Under Attack 모드** — 프로브의 User-Agent가 `Mublo-Domain-Verify/1.0`(비브라우저)이라
   챌린지(403·503)를 받으면 확인이 실패합니다. `/.well-known/` 경로를 예외로 두고 다시 시도하세요.
2. **인증서 발급 직전** — 프록시에 도메인을 막 연결한 직후에는 TLS가 준비되지 않을 수 있습니다. 잠시 후 재시도하세요.

확인 결과는 `domain_verifications` 테이블에 기록되고 **30분간** 유효하며 **1회만** 사용됩니다.
변경 API가 이 기록을 다시 확인하므로, 화면을 조작해 확인을 건너뛸 수는 없습니다.

### 변경 이력

실제 변경까지 간 검증 기록은 `status='consumed'`로 마감되면서 감사 정보가 채워집니다.

| 컬럼 | 내용 |
|------|------|
| `consumed_at` | 변경 시각 |
| `previous_host` → `host` | 이전 호스트명 → 바뀐 호스트명 |
| `consumed_by` | 변경을 실행한 관리자 |
| `requested_by` | DNS 확인을 요청한 관리자 (실행자와 다를 수 있음) |
| `verdict` / `dns_result` / `probe_result` | 무엇을 근거로 통과시켰는지 |

`requested_by`와 `consumed_by`를 나눠 두는 이유는 최고관리자가 여러 명일 수 있고, 검증은
호스트명 기준으로 찾으므로 A가 확인한 기록을 30분 안에 B가 변경에 사용할 수 있기 때문입니다.

이 이력은 **도메인(호스트명) 변경** 카드 안에 최근 10건까지 표시됩니다. **확인만 하고 변경하지
않은 시도(`pending`/`passed`/`failed`)는 이력에 나오지 않습니다** — 변경 이력과 확인 시도 기록이
섞이면 감사 목적이 흐려지기 때문입니다(그 기록들은 테이블에 그대로 남아 조회 가능합니다).
같은 내용이 감사 로그 `storage/logs/D{domain_id}/domain/{날짜}.log`에도 `verification_id`와 함께 남습니다.

`dev_local` 생략은 `APP_ENV`로만 판정합니다(`APP_DEBUG`가 아닙니다). `APP_DEBUG`는 운영에서
장애 진단을 위해 일시적으로 켤 수 있는 값이라, 그때 검증 게이트가 느슨해지면 안 되기 때문입니다.
`APP_ENV` 미설정 시 기본값은 `production`이며, 화이트리스트에 없는 값(오타 포함)은 생략을
허용하지 않습니다.

프로브 응답 경로는 `/.well-known/mublo-domain-verify` 이며, 아직 등록되지 않은 호스트로
들어오는 요청에도 답해야 하므로 도메인 검증을 우회합니다. 유효한 nonce가 없으면 404입니다.

### 변경 직후

- **자기 사이트**: 세션 쿠키는 호스트별이라 옛 주소의 로그인 상태를 새 주소에서 쓸 수 없습니다.
  그래서 일회용(30초) 인계 토큰이 담긴 새 주소로 자동 이동해 같은 계정으로 다시 로그인됩니다.
  (대리 로그인이 아니므로 상단 배너는 뜨지 않습니다.)
- **하위 사이트**: 현재 접속 주소는 그대로이므로 목록으로 돌아옵니다.
- **옛 주소**: 더 이상 이 사이트로 연결되지 않습니다(`등록되지 않은 사이트`).
  옛 주소를 함께 살려두는 별칭(alias) 기능은 아직 없습니다.
- 도메인 해석 캐시(구·신 양쪽)와 옛 도메인의 라우트 캐시는 자동 정리됩니다.
  업로드 파일(`D{domainId}`)·데이터 캐시는 도메인 ID 기준이라 영향이 없습니다.

### 주의

- 현재 접속 중인 사이트의 **운영 상태**는 이 화면에서 바꿀 수 없습니다
  (스스로를 비활성·차단해 관리자 접속이 끊기는 것을 막기 위함).
- 웹서버(nginx 등)가 새 호스트명의 요청을 이 애플리케이션으로 넘기도록 설정돼 있어야
  도달 확인이 통과합니다.

## 도메인별 설정

각 도메인은 독립적인 설정을 가집니다.

### 사이트 설정 (siteConfig)
- 사이트 제목, 부제목
- 로고 이미지 (PC/모바일)
- 파비콘, OG 이미지

### 회사 정보 (companyConfig)
- 회사명, 대표자, 사업자등록번호
- 주소, 전화번호

### SEO 설정 (seoConfig)
- 메타 설명, 키워드
- 검색엔진 노출 여부

### 테마 설정 (themeConfig)
- 프론트 프레임 스킨
- 관리자 스킨

### 확장 설정 (extensionConfig)
- 활성화된 패키지 목록
- 활성화된 플러그인 목록
- 도메인별로 다른 패키지/플러그인 조합 가능

## 도메인 격리

| 대상 | 격리 방식 |
|------|----------|
| 회원 | `domain_id`로 완전 분리. A 도메인 회원이 B에 로그인 불가 |
| 게시판 | 도메인별 독립 게시판, 게시글 |
| 블록/페이지 | 도메인별 독립 메인 페이지 |
| 메뉴 | 도메인별 독립 네비게이션 |
| 파일 | `public/storage/D{domainId}/` 하위에 분리 저장 |
| 캐시 | 도메인 ID 기반 캐시 키 분리 |
| 세션 | 도메인별 세션 이름 분리 |

## 도메인 그룹

도메인 간 계층 구조를 설정할 수 있습니다 (`domainGroup` 필드). 상위 도메인 관리자가 하위 도메인을 관리하는 용도로 사용합니다.

## 도메인 상태

| 상태 | 설명 |
|------|------|
| active | 정상 운영 |
| inactive | 비활성 (관리자만 접근 가능) |
| blocked | 차단 (모든 접근 불가) |

계약 기간이 만료되면 자동으로 접근이 제한됩니다.
