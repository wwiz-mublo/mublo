# Mublo 철학

Mublo Framework의 핵심 철학은 단순합니다.

> Core는 가볍게, 확장은 자유롭게.

Mublo는 모든 기능을 Core에 넣는 방식이 아니라, Core가 안정적인 실행 규칙과 확장 지점을 제공하고 실제 기능은 Plugin과 Package가 담당하는 방식을 지향합니다.

## Core는 가볍게

Core는 다음 책임에 집중합니다.

- 요청 흐름과 애플리케이션 부팅
- 라우팅과 Dispatcher
- DI 컨테이너
- Context와 도메인 해석
- 인증, 세션, CSRF 같은 공통 보안 기반
- Response와 View 렌더링
- EventDispatcher와 ContractRegistry
- BlockRegistry와 블록 렌더링 기반
- 관리자 운영 기반

Core는 게시판, 쇼핑몰, 팝업, 배너 같은 구체적인 업무 기능을 직접 품으려 하지 않습니다. 이런 기능은 독립 확장 모듈로 분리합니다.

## 확장은 자유롭게

확장은 두 종류로 나뉩니다.

| 구분 | 역할 | 예시 |
|------|------|------|
| Plugin | 작고 수평적인 기능 확장 | 배너, 팝업, FAQ, 소셜 로그인, 포인트, 통계 |
| Package | 자체 업무 영역을 가진 독립 애플리케이션 | Board, Shop |

Plugin과 Package는 동일하게 Provider를 통해 Core에 연결됩니다.

- `register()`에서 서비스와 구현체를 DI 컨테이너에 등록합니다.
- `boot()`에서 이벤트 구독자, 블록 콘텐츠 타입, Contract 구현체를 연결합니다.

이 규칙 덕분에 기능은 자유롭게 추가되지만, Core의 실행 흐름은 가볍고 예측 가능하게 유지됩니다.

## 연결은 느슨하게

Mublo는 전역 문자열 훅으로 어디서든 끼어드는 구조를 지양합니다.

대신 두 가지 연결 방식을 명확히 구분합니다.

| 연결 방식 | 의미 | 사용 예 |
|-----------|------|---------|
| Event | 어떤 일이 발생했음을 알림 | 회원가입 완료, 주문 상태 변경, 관리자 메뉴 구성 |
| Contract | 특정 기능이나 데이터를 호출 | 결제 게이트웨이, FAQ 조회, 알림 발송 |

상태 변화에 반응해야 하면 Event를 사용하고, 값을 받아야 하거나 특정 기능을 호출해야 하면 Contract를 사용합니다.

## 운영은 블록으로 유연하게

Mublo의 블록 시스템은 개발자가 만든 기능을 운영자가 직접 조합할 수 있게 하는 편집 계층입니다.

- 개발자는 블록 콘텐츠 타입을 등록합니다.
- Package/Plugin은 선택 가능한 아이템을 공급합니다.
- 운영자는 관리자에서 행, 열, 콘텐츠 타입, 스킨, 아이템을 조합합니다.

즉, 개발자는 확장 가능한 재료를 만들고 운영자는 화면을 구성합니다.

## 확장의 무대는 Core가, 무대 위는 확장이

"Core는 가볍게"는 "작게"가 아닙니다. Core는 업무 기능을 품지 않는 대신, **모든 확장이 공정하게 설 무대는 Core가 소유합니다** — 활성화 상태, 설치 라이프사이클, 보안 게이트, 확장 화면 같은 것들입니다. 무대가 하나여야 운영자의 경험과 개발자의 작법이 어느 확장에서나 같아집니다.

반대로 무대 위의 내용 — 무엇을 제공하고, 어디에 두고, 어떻게 구성할지 — 는 확장이 결정합니다. 패키지 종속 플러그인이 이 분업의 예입니다: 패키지가 자기 플러그인을 수용할지, 어떤 플러그인이 있는지는 **패키지가 답하고**(`PluginHostInterface`), Core는 그 답을 신뢰해 실행만 합니다. Core는 메커니즘을, 확장은 정책을 소유합니다.

이 원칙 덕분에 패키지 개발자는 자기 패키지 위에 **자기만의 확장 생태계**를 열 수 있습니다 — 게시판 패키지에 다른 개발자가 신고 플러그인을 배포하는 식으로. 생태계는 Core 위 한 층이 아니라, 패키지 수만큼 곱해지는 구조입니다.

## 호환성 서약

확장 생태계를 여는 프레임워크의 첫 번째 의무는 **깨지 않는 것**입니다. 확장 개발자의 노력과 생계가 이 서약에 걸립니다.

- **안정 표면은 깨지 않습니다.** 안정으로 분류된 Event, Contract 인터페이스, manifest 규격, 블록 렌더 마커, Provider 계약이 안정 표면입니다. 무엇이 안정인지는 [호환성 정책](compatibility-policy.md)이 명시합니다.
- **깨야 할 때는 예고하고, 길을 냅니다.** 안정 표면의 파괴적 변경은 메이저 버전에서만 하며, 변경 이유·마이그레이션 방법을 릴리스 노트에 함께 제공합니다.
- **내부는 자유롭게 바꿉니다.** 안정 표면 바깥(내부 클래스·비공개 이벤트)에 의존한 확장은 보호 대상이 아닙니다 — 그래서 확장은 안정 표면만 사용해야 합니다 ([확장 필수사항](dev-guide/extension-requirements.md)).

이 서약은 기능이 아니라 약속이고, 오래 지킬수록 가치가 커지는 종류의 자산입니다.

## 멀티 도메인은 운영 확장성

멀티 도메인은 Mublo의 중요한 기능이지만, 철학의 출발점은 아닙니다. Mublo의 중심은 확장 구조이고, 멀티 도메인은 그 구조가 실제 운영 환경에서 여러 사이트를 다룰 수 있게 해 주는 운영 확장성입니다.

하나의 코드베이스에서 도메인별 설정, 회원, 권한, 테마, 활성 확장을 분리할 수 있습니다.

## 설계 판단 기준

새 기능을 추가할 때는 다음 순서로 판단합니다.

1. Core에 꼭 있어야 하는 공통 실행 규칙인가?
2. Plugin이나 Package로 분리할 수 있는 업무 기능인가?
3. 상태 변화 후처리라면 Event로 충분한가?
4. 값을 받아야 하는 호출이라면 Contract가 맞는가?
5. 운영자가 조합해야 하는 출력이라면 Block으로 드러낼 수 있는가?

이 기준이 Mublo의 구조를 오래 유지하는 안전장치입니다.
