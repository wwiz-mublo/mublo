# PayApp (페이앱)

[페이앱](https://www.payapp.kr) 결제를 Mublo 의 결제 계약(`PaymentGatewayInterface`)으로 연결하는 플러그인입니다.

쇼핑몰 같은 소비 패키지는 이 플러그인을 직접 알지 못합니다. 체크아웃에서 PG 키 `payapp` 을 고르면 결제창을 열고, 결제 결과는 페이앱 서버의 통보(feedbackurl)로 받아 소비 패키지에 계약(`PaymentConsumerInterface`)으로 넘깁니다.

- **요구 사항**: Mublo Core 1.0.0 이상, 페이앱 판매자 계정, 외부에서 HTTPS 로 접근 가능한 사이트 주소
- **설치 후 메뉴**: 관리자 → 플러그인 → 페이앱 → 결제 설정 (`/admin/pay-app/settings`)

## 무엇을 하는가

| 영역 | 내용 |
|------|------|
| 결제 준비 | `payrequest` 로 결제요청번호(`mul_no`)와 결제창 주소를 받아 팝업으로 연다 |
| 결제 확정 | 페이앱 서버 → 사이트 통보(`pay_state=4`)를 받아 소비 패키지가 검증·주문 확정 |
| 취소 | 전체취소·부분취소(`paycancel`) |
| PG 측 취소 반영 | 페이앱 관리 화면에서 일어난 취소 통보를 소비 패키지 장부에 기록 |
| 설정 | 도메인(사이트)마다 자기 판매자 계정 키를 등록. 다른 도메인 설정으로 대체하지 않는다 |

### 결제수단

결제창에 여는 수단은 `openpaytype` 으로 지정합니다.

`card, phone, kakaopay, naverpay, smilepay, rbank, applepay, payco, wechat, myaccount, tosspay`

(신용카드, 휴대전화, 카카오페이, 네이버페이, 스마일페이, 계좌이체, 애플페이, 페이코, 위챗페이, 내통장결제, 토스페이)

페이앱 문서상 **판매자 사이트의 결제 설정이 우선**합니다. 판매자 사이트에서 끈 수단은 여기 있어도 열리지 않습니다.

> **가상계좌는 지원하지 않습니다.**
>
> 가상계좌는 발급(`pay_state=10`)과 입금(`pay_state=4`) 사이가 깁니다. 이 플러그인은 입금 대기
> 주문을 붙잡아 둘 경로를 갖고 있지 않아, 발급된 채로 두면 소비 패키지가 결제시도 주문을 스윕한 뒤
> 입금만 들어오는 **주문 없는 돈**이 됩니다. 그래서 결제창에서 빼고(`vbank` 제외), 그래도 발급
> 통보가 오면 발급을 즉시 취소합니다. 나나결제(`dvpay`, 분할결제)도 열지 않습니다.

## 설정

관리자 → 페이앱 → 결제 설정. 값은 **페이앱 판매자 관리 사이트 → 설정 → 연동정보**에서 확인합니다.

| 항목 | 필수 | 설명 |
|------|------|------|
| 판매자 아이디 (`userid`) | 필수 | 페이앱 판매자 회원 아이디 |
| 연동 KEY (`linkkey`) | 필수 | API 호출 인증 키. 암호화 저장 |
| 연동 VALUE (`linkval`) | 필수 | 통보 검증값. 암호화 저장 |
| 결제 KEY (`requestkey`) | 권장 | 넣으면 통보의 위변조 방지 해시(`hash`)를 검증하고, 취소 요청에 해시를 싣는다. 암호화 저장 |
| 송신 IP 허용목록 | 권장 | 페이앱 발신 IP 만 받는다. 쉼표·공백 구분, CIDR(`1.2.3.0/24`) 가능. 비우면 모든 IP 허용 |

- 세 필수값 중 하나라도 비어 있으면 결제를 열지 않고(`NOT_CONFIGURED`), 그 도메인 앞으로 온 통보도 받지 않습니다(403).
- 비밀값(연동 KEY·VALUE·결제 KEY)은 설정 화면에 다시 표시하지 않습니다. 빈 칸으로 저장하면 기존 값이 유지되고, 바꿀 때만 입력합니다.
- 페이앱은 sandbox 가 없어 항상 운영 모드입니다.

### 통보 주소(feedbackurl)

결제를 요청할 때마다 `https://{사이트}/pay-app/callback/feedback?by={소비자 키}` 를 `feedbackurl` 로 함께 보냅니다. **페이앱 관리 화면에 따로 등록할 필요는 없습니다.**

- 외부에서 HTTPS 로 접근할 수 있어야 합니다. 방화벽·접근 제한이 있으면 결제 완료를 받지 못합니다.
- 판매자 사이트의 **공통 통보 URL** 에 이 주소를 넣지 마십시오. 공통 통보에는 소비자 키(`by`)가 없어 처리되지 않고 재전송만 반복됩니다.
- `checkretry=y` 로 요청하므로, 사이트가 `SUCCESS` 가 아닌 응답을 하면 페이앱이 재전송합니다(문서: 최대 10회).

## 결제 흐름

```
체크아웃 (소비 패키지)
  └ prepare()  ── payrequest ──▶ 페이앱      mul_no, payurl
                                  │
  브라우저: 결제창 팝업 ──────────▶│ 결제
                                  │
  /pay-app/callback/feedback ◀─────┘ 통보 (서버→서버 POST)
    ├ 인증: 도메인 설정 존재 → IP 허용목록 → userid/linkkey/linkval(+hash)
    ├ 4  결제완료 ─▶ verifyPayment (소비 패키지: payinfo 재조회·주문번호·금액 대조 → 주문 확정)
    ├ 10 결제대기 ─▶ 가상계좌 발급 → paycancel 로 발급 취소
    ├ 9·64 승인취소 / 70·71 부분취소 ─▶ payinfo 확인 → recordExternalRefund
    └ 1·8·16·31·32 요청·요청취소 ─▶ 결제 전 — 기록 없음

  팝업은 결제 후 /pay-app/callback/return 으로 와서 스스로 닫힌다
  └ 부모창이 팝업 닫힘을 감지해 소비 패키지의 결제 상태 확인을 부른다(보조 경로)
```

결제 성공 여부의 권위는 통보와 PG 조회(`payinfo`)에 있습니다. 복귀 화면(`return`)은 "결제창이 끝났다"는 사실만 압니다.

## 안전장치

| 상황 | 처리 |
|------|------|
| 연동 정보가 없는 도메인을 지목한 통보 | 403. 도메인은 통보 본문(`var2`)에서 오므로, 빈 설정끼리의 비교로 위조가 통과하지 않게 검증 전에 막는다 |
| 연동 값 불일치·IP 허용목록 밖 | 403 |
| 결제완료인데 소비 패키지 검증 실패 | ① 이미 결제 완료로 반영됐는지 재확인 ② 페이앱 조회로 결제완료·같은 주문번호(`var1`)인지 확인 ③ 한 번 더 검증 ④ 그래도 실패면 **전액 자동 취소** |
| 자동 취소 실패 | `[PayApp][CRITICAL]` 로그(`mul_no`·주문번호·사유). 관리자가 페이앱에서 직접 환불해야 한다 |
| 주문 없이 들어온 가상계좌 입금 | 위와 같은 경로로 자동 취소를 시도하고, 못 하면 CRITICAL 로그에 은행·계좌를 함께 남긴다 |
| 페이앱 조회상 다른 주문의 결제 | 자동 취소하지 않는다(남의 결제를 취소하지 않음). CRITICAL 로그 |
| 환불 통보 | 소비 패키지가 아는 주문의 PG 가 페이앱인지, 페이앱 조회로 그 결제가 이 주문 것(`var1`)이고 실제 취소 상태인지 확인한 뒤에만 기록 |
| 로그 | 통보 본문의 `linkkey`·`linkval`·`hash` 는 가려서 남긴다 |

### 응답 원칙

| 응답 | 언제 |
|------|------|
| `SUCCESS` (200) | 처리했거나, 다시 보내도 결과가 같은 실패(자동 취소·CRITICAL 로그를 남김) |
| `FAIL` (500) | 일시 오류 — 예외(DB 장애 등), 페이앱 조회 실패, 취소 통신 실패, 환불 기록 실패. 재전송으로 다시 처리한다 |
| `FAIL` (403) | 인증 실패 |

결제 검증과 환불 기록은 소비 패키지 쪽에서 멱등이라 재전송이 와도 두 번 반영되지 않습니다. 쇼핑몰(Shop)의 환불 기록은 같은 거래번호·같은 종류의 성공 기록이 있으면 다시 쓰지 않고, 이미 전액 환불된 주문은 건너뜁니다.

## 취소 / 부분취소

소비 패키지가 `cancel($transactionId, $amount, $reason, $remainingAmount)` 를 부릅니다.

| 조건 | 요청 |
|------|------|
| `amount <= 0` | 전체취소 (`partcancel=0`) |
| `remainingAmount` 를 알고 `amount >= remainingAmount` | 전체취소 |
| 그 밖 | 부분취소 (`partcancel=1`, `cancelprice=amount`) |

잔액을 모르면 금액이 있는 한 부분취소로 보냅니다. 확인할 수 없는데 전체취소로 보내면 요청보다 많이 돌려줄 수 있기 때문입니다.

페이앱 문서상 판매자 정산이 끝난 결제는 `paycancel` 로 취소되지 않습니다(별도 `paycancelreq` 절차). 이 플러그인은 그 절차를 구현하지 않았으므로 이 경우 취소는 실패로 돌아옵니다.

## 알려진 제약

다음은 페이앱 개발자센터 문서(2026-11 확인)로 **확인하지 못한 가정**입니다.

- **부분취소 통보의 번호·금액** — 문서는 부분취소 통보에 원거래 번호 `orig_mul_no`·원거래 금액 `orig_price` 가 온다고 하고, 예제는 `price` 를 취소 금액으로 씁니다. 그래서 통보의 `mul_no` 를 부분취소 건 자신의 번호로 보고 장부의 거래번호로 쓰며, 확인 조회는 `orig_mul_no` 로 합니다. 실제 부분취소 통보로 검증하지 않았습니다.
- **조회(`payinfo`) 응답** — `usingstate`·`var1`·`goodprice` 를 쓰는 것은 기존 구현의 관측에 따른 것이고, 이번 문서 페이지에는 `payinfo` 명세가 없습니다. 부분취소 뒤 원거래의 `usingstate` 가 무엇이 되는지도 확인하지 못해 4·9·64·70·71 을 모두 받아들입니다.
- **가상계좌 발급 취소** — 결제대기(`pay_state=10`) 건에 `paycancel`(전체)이 먹는다고 가정합니다. 문서의 `paycancel` 은 "결제(요청,승인) 취소"이고 `cancelmode=ready` 는 "결제요청 상태만 취소"라고만 되어 있습니다.
- **`openpaytype` 과 판매자 설정** — 문서상 판매자 설정이 우선합니다. 판매자 사이트에서 가상계좌를 켜 두면 결제창에 나올 수 있다고 보고 서버 쪽 취소 방어를 함께 두었습니다.
- **API 주소** — 현재 문서의 REST 주소는 `https://api.payapp.kr/oapi/v2` 이고 취소 요청에 `requestdate`·`hash` 를 필수로 적고 있습니다. 이 플러그인은 기존 주소(`/oapi/apiLoad.html`)를 그대로 쓰며, 결제 KEY 를 등록한 경우에만 `requestdate`·`hash` 를 싣습니다.
- 구매자 이름을 받는 필드는 문서에 없습니다(`buyerid` 는 아이디). 이메일만 `recvemail` 로 넘깁니다.

그 밖의 제약:

- 쇼핑몰 장부의 환불 멱등 가드는 거래번호·종류 단위입니다. 사이트에서 부분취소한 뒤 같은 취소의 통보가 다른 거래번호로 오면 이중 기록될 수 있습니다(잔액을 넘지는 않음). 소비 패키지 쪽 과제입니다.
- 통보의 `responsedate` 시각 유효성은 보지 않습니다(재전송이 시간을 두고 오기 때문).

## 변경 이력

### 1.0.1

- **보안**: 연동 정보가 없는 도메인을 지목한 위조 통보가 빈 값 비교로 통과하던 문제를 막았다. 설정값이 하나라도 비면 검증이 실패하고, 그런 도메인 앞 통보는 403 으로 거부한다.
- **보안**: 결제 KEY(선택)를 등록하면 통보 `hash` 를 검증한다. 환불 통보는 페이앱 조회로 주문·취소 상태를 확인한 뒤에만 기록한다.
- **결제**: 가상계좌를 결제창에서 빼고, 발급 통보가 오면 발급을 취소한다(주문 없는 입금 방지).
- **결제**: 결제완료 후 주문 반영이 실패하면 재확인 뒤 전액 자동 취소, 실패 시 CRITICAL 로그.
- **결제**: 요청취소(8·32 등, 결제 전)를 환불로 기록하던 문제를 고쳤다. 환불 기록 실패·일시 오류는 FAIL 로 재전송을 받는다. 결제 요청에 `checkretry=y` 를 실어 재전송이 실제로 일어나게 했다.
- **취소**: 잔액 전부를 취소하면 전체취소로 보낸다(전에는 금액이 있으면 늘 부분취소).
- **설정**: 연동 VALUE 없이 결제가 열리던 문제를 고쳤다. 비밀값은 화면에 표시하지 않고 빈 칸 저장 시 유지한다.
- **로그**: 통보 본문의 `linkkey`·`linkval`·`hash` 를 가린다.
- 구매자 이메일을 `recvemail` 로 넘긴다. 통보 결제수단 코드를 문서 표(1 신용카드·2 휴대전화·7 가상계좌…)로 고쳤다.

### 1.0.0

- 첫 공개.
